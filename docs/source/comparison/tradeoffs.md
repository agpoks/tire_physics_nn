# Trade-offs: what to use when

A summary of the whole documentation in two tables and a decision path.

## By modelling approach

| | accuracy on rich data | accuracy on sparse data | guarantees | interpretability | cost | extrapolates |
|---|---|---|---|---|---|---|
| linear | poor | good near zero | unbounded | total | trivial | no |
| brush / Dugoff | fair | fair | bounded, symmetric | high | trivial | gracefully |
| Magic Formula (fitted) | excellent | **poor** (ill-conditioned) | bounded, symmetric | high | cheap | no |
| black-box MLP | excellent | poor | **none** | none | cheap | badly |
| MLP + penalty | excellent | poor | soft, unreliable | none | cheap | badly |
| symmetry-encoded | excellent | fair | shape only | low | cheap | shape holds |
| symmetry + envelope | excellent | good | shape + bound | medium | cheap | properties hold |
| ParameterNet + law | excellent* | **excellent** | all of the law's | **total** | cheap | as well as the law |
| residual grey box | excellent | good | shape + bound | high (decomposed) | cheap | as well as the baseline |

\* on data generated by that law — see the [benchmark caveat](benchmarks).

## By physical effect

| effect | cheapest adequate model | when you need more |
|---|---|---|
| force vs slip | brush or Magic Formula | measured post-peak decay, camber, pressure → MF 6.x |
| combined slip | similarity method | you have a full combined-slip measurement set → MF weighting functions |
| load dependence | $\mu(F_z)$ load sensitivity | large load range, aero → measured load sweeps |
| transient | first-order relaxation | belt vibration above ~30 Hz → rigid-ring model |
| temperature | two-node thermal | tread-depth gradients, blistering → multi-node or 1-D diffusion |
| wear | monotone scalar state | compound-specific wear rates → dedicated wear model |
| graining | reversible bounded state | anything quantitative → **you need real data; this framework has none** |
| vehicle | four-wheel Newton–Euler | roll, pitch, suspension kinematics → multi-body |

## Decision path

**Do you have tire-force measurements?**

*Yes, and plenty across the operating envelope* → `EncodedTireNet` if you want maximum
flexibility with guarantees; `ParameterTireNet` if you want to hand coefficients to a
controller. Both are equally accurate here; choose on what you need downstream.

*Yes, but sparse or over a narrow range* → `ParameterTireNet`. The bounded
parameterisation is what makes it usable at 210 samples where a direct fit fails.

*Yes, plus an existing analytical model you trust* → `ResidualTireNet`, and watch
`residual_fraction`.

*No, only vehicle logs* → `FourWheelVehicle` around a shared tire, warm-started from rig
data if any exists. Expect identification only over the slip range the vehicle visited.

**Then, do you have transients that matter?** Wrap in `RelaxationTireCell`. It costs two
parameters and a sequential rollout, and it is the difference between a model that
transfers across speed and one that does not.

**Then, does condition change within your data?** Wrap in `ThermoGrainingTire`, enabling
only the states you can actually supervise. With none enabled it reduces exactly to the
static model.

## What this framework will not do for you

- **It will not invent data.** Vehicle-level identification only sees the slip range the
  car visited; the friction limit is unobservable if you never approached it.
- **It will not fix a wrong chassis.** The mechanics are exact by design, so a wrong
  $I_z$ or track width shows up as a fit error rather than being absorbed — which is the
  intent, but it means you must measure the vehicle properly.
- **It will not validate graining.** The condition model is structurally sound and
  entirely unvalidated against real motorsport data.
- **It will not make a black box safe by adding a penalty.** That is the one negative
  result this project states most confidently — see [benchmarks](benchmarks).
